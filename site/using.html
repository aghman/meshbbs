02 Using it

You already have the client

Two front doors onto one BBS. SSH brings its own conveniences — public-key login means no password to remember, and SFTP comes free as the file-area transport. A browser reaches the same screens, the same menu graph and the same people, rendered for a screen that can wrap text instead of an 80-column grid.

Getting in

Three ways an account starts

This is the one place SSH is genuinely worse than telnet for a BBS. A classic board lets you connect and type NEW at the login prompt; SSH decides accept-or-reject before any session exists, so there is no prompt to type it at. Registration is handled at the auth layer instead.

On the web it inverts — there's a page, and a page can prompt for anything. What's missing there is the key, which is why the browser front door uses passkeys.

The menu is the same graph for everyone — a guest sees every entry and is turned away at the ones that need an account, rather than being shown a shorter board. Two entries are conditional: [P] appears only when the sysop has enabled the web front end, and [S] Sysop panel only for the sysop.

Nicks are local
austin@K7QM4X2PB9TFR and austin@M2X9F0QLD4H7A are different people. Registration therefore needs no network coordination at all — no name reservation, no distributed lock, no waiting on a mesh round-trip. A brand-new instance with no radio and no peers can create accounts immediately.
Nick rules
2–16 characters from [A-Za-z0-9_-], starting with a letter. Unique within the instance, case-insensitively. Display names are separate and may be richer.
Reserved
new, guest, sysop, admin, root, bbs, all, postmaster, daemon
Typing a nick that doesn't exist
ssh marguerite@bbs for an account nobody has taken drops you into registration with that nick already filled in, rather than returning an opaque permission denied. If the nick does exist and your key is not enrolled on it, you get a different screen telling you to log in with your password and enrol the key — never the signup flow. Offering "register?" to someone whose key merely changed is how you get duplicate accounts.
Registration modes
The default is open with federated posting withheld — the door is open, the shared airtime is gated. A sysop grants post_federated when they're ready to spend budget on you. The config accepts approval and invite as well, but neither flow is built yet: today anything other than open simply closes self-registration.
Multiple keys
Enrol one per client, from a session you are already logged into. Your laptop and your phone can both be you.
Themes are the sysop's
Four ship — classic, contrast, mono, muted — and the instance picks one for every session. There is no per-user theme picker. Character encoding is per-session: UTF-8 or CP437, guessed from your locale and terminal type.
Message bases

Forums, and which ones leave the building

Areas — echo areas, conferences, whatever your era called them — are the unit of replication. Each has a name, a description, a moderation policy, and a list of peer nodes it federates with.

New areas default to local-only. A sysop has to opt in to burning airtime, and at this budget that default is doing real work. A local area never touches the radio no matter how busy it gets.

Threading is by parent pointer and the interface rebuilds the tree. Out-of-order arrival is completely normal on a mesh, so a reply whose parent hasn't landed yet renders as parent not yet received and re-parents itself when it turns up — that's expected behaviour, not an error.

No merge conflicts

Records are immutable. An edit is a new record pointing at what it supersedes; a delete is a signed tombstone. Two instances can never disagree about what a post says.

Posts are node-signed

"The instance holding key K7QM4X2P… vouches that user austin posted this." That matches the FidoNet trust model — you trust the sysop, and the sysop is accountable.

Per-area airtime shares

One chatty area could otherwise starve every other one. Each federated area gets a slice of the node's allocation, so busy and quiet areas coexist.

Private messages

Mail the sysop can't read

Private messages are end-to-end encrypted and user-signed. Intermediate BBSes and everyone else on the mesh channel store and forward opaque bytes — subject lines included.

Address them nick@NODEID, or nick@alias if your sysop has named the peer. Undeliverable mail to a peer that has not been heard from is queued rather than refused — the retry and bounce policy is a Phase 5 concern and is not built yet, so today the honest description is that mail to an unreachable node waits.

Where key custody is concerned there's a genuine tension, and it's worth being straight about: the product is a terminal session, so if the server never holds your key, the server can't render your mail. Three tiers ship in order.

Stated plainly, because it should be

Under the default tier your private key is stored wrapped by a passphrase only you know, so at rest the sysop has ciphertext. But during a session the plaintext key is in server memory — unavoidable if the server is the thing drawing the message on your screen. Tier 3 removes even that, at the cost of running a helper locally.

Separately: who you message is not private. Other sysops can see that you messaged someone and when. That's a deliberate trade — it's what lets an intermediate node bounce undeliverable mail immediately instead of holding it blind.

File areas

You see the whole network's files

File areas work over SFTP or through an in-terminal browser. The blob store is content-addressed, so the same file uploaded to three areas is stored once.

Over mesh, only the catalog replicates. File records carry name, size, hash, description, tags and which node holds it — 120 to 200 bytes compressed. So you browse the entire network's file list from any instance, and fetching is a separate question with exactly two answers.

Held by is the column that carries the whole idea. It says here for a file this BBS has the bytes of, and names the peer for one it only knows the listing of — and in that second case the detail screen says so plainly instead of offering a download that would spin forever.

The design's two fetch paths are a direct IP connection to a holding BBS, or the sneakernet queue — a request recorded and satisfied at the next bundle exchange, which might be someone walking a USB stick between two sites. Neither is built yet: both are later phases, so today the browser names the holding BBS and its sysop and leaves it there, rather than promising a queue nothing would service. What is already true is the part that will not change — there is no third path, and no size threshold below which the mesh will carry bytes.

Doors

Door games, and the reason to care

A door is any executable in any language. It talks over stdin and stdout with the BBS bridging your terminal, and gets session context — handle, node number, time remaining, terminal size, ANSI capability — through environment variables and a JSON descriptor. Identical on Linux, macOS and Windows.

The payoff is inter-BBS leagues. Classic BBS culture had LORD wars and TradeWars leagues that exchanged score files over FidoNet; the same federation bus works here, so you can have an inter-BBS door league running over LoRa mesh with no internet involved. That's very nearly free once the sync protocol exists.

What a door is allowed to do

Doors are third-party binaries running on the sysop's machine on your behalf. Three capability levels are always available; the fourth is granted per door and off by default.

LevelWhat it can doGranted
session Read context only — handle, node number, time remaining, terminal size. No writes always
state A private key/value space scoped to this door and this user, with a quota. No reach across doors or users always
announce Post to a designated area as the door itself, never as you — rendered TRADEWARS (door@K7QM4X2P…) so it's attributable and rate-limitable always
act_as_user Post or send mail as you. What makes a league feel native — and also a door impersonating a person sysop grant

Capabilities intersect and never escalate: a door acting as a user who lacks post_federated cannot federate on their behalf. Every level-4 action is audit-logged, and you are told the first time a given door posts as you — a notice, not a log entry you'll never read.

Web access

The same BBS, in a browser

Not a terminal emulator in a web page. The screens themselves became a typed description of what you're looking at, and there are now two renderers for it: one draws ANSI for SSH, one builds DOM for the browser.

That distinction is the whole point. The model emits a full area name and a hint about the column; SSH cuts it to 26 characters, and the browser shows all of it and lets CSS handle the overflow. A post wraps at a comfortable measure rather than at column 78. A mail list scrolls rather than pages.

And because there's one navigation model rather than two, a screen cannot exist over SSH and be missing from the web — there's nowhere for it to be missing from. The ANSI renderer is held to byte-identical output by the golden-frame tests, so the terminal experience didn't shift to make room for the browser.

Everything is a keystroke

Clicking the [M] row sends m. Tapping enter open sends enter. The server never learns it was a click, so there is no browser-only path through the BBS.

You're in the same room

A browser session gets a node number and appears in Who's Online next to everyone else, in the same chat. One BBS, three doors.

Shipped in the binary

The whole front end is embedded — no CDN, no build step in the release path, nothing fetched from anyone else at page load.

Signing in is a passkey, and nothing else

No password path, no SSH-key path. The credential is a keypair whose private half the server never holds — the same shape as SSH key auth, and as the node identity itself. Since the credentials are discoverable, you don't type a nick either: press sign in, answer whatever unlocks your device, and you're through.

Which leaves one problem: a passkey has to be registered from a browser by someone already established as the account holder, so passkeys can't bootstrap themselves. Every account that predates the web needs a way across.

The URL in that screen is whatever the sysop set as web.origin — here a loopback instance, which is the one case a browser accepts without a certificate. The [P] entry does not appear in the menu at all until the web front end is on.

What that code can and can't do

It registers a credential and nothing else — no endpoint will trade it for a session, so it can't be replayed as a bearer token. It's single-use, one live code per account, expires in ten minutes, and is stored hashed like any other credential.

Read "it cannot log anyone in" precisely, though: the code is not a bearer token, and no endpoint trades it for a session. It is not a claim that a stolen code is harmless. An earlier draft of the design said a stolen code "gets an attacker no session", and that was wrong — someone holding a live code can register their own passkey on your account and sign in with it whenever they like. That is what enrolling a credential means, and no arrangement of endpoints changes it. The protection is the ten-minute window and the fact that only an already-authenticated session can mint one.

Two consequences worth knowing up front

There's no guest browsing on the web. A passkey-only front door means a visitor without an account sees a sign-in prompt and nothing else. The SSH guest account still exists, but the web is not currently a way to show a board off to a stranger. That's a product decision rather than a technical limit.

A closing browser tab is a poor goodbye. Unlocking your mail puts the passphrase in server memory exactly as it does over SSH — but a killed tab, a locked phone or a sleeping laptop may never send a proper close. So the idle timer is doing real security work here, and a session with mail unlocked times out sooner (10 minutes) than one sitting in a forum (30).

If your client is picky

Telnet exists for the ANSI terminal clients BBS people actually use — SyncTERM, NetRunner, MagiTerm — which are telnet-only. It's off by default, and when a sysop enables it both the login banner and the startup log state that credentials cross the wire in plaintext. Guest-only telnet is a supported middle setting and the recommended one: browsing over plaintext costs nothing, typing a password over it does.
