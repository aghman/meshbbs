Federation

Peering, when there is nothing to register

There is no registration, no pairing ceremony and no authority to ask. A node's ID is its key, so there is nothing to squat, no binding to maintain and no way for a different key to answer to an ID. What is left for a sysop to do is small, and this page is all of it.

Expectations

Nobody grants you a peer

In most federated systems, peering is a handshake: two operators agree, exchange credentials, add each other to a list. Here it is closer to tuning to a frequency. Two instances federate when they are on the same bbsnet channel with the same key and have federated areas whose names match. That is the whole mechanism.

So the sysop work is not establishing peers — it is recognising them: knowing which board a node ID belongs to, giving it a name you will remember, and checking that the board calling itself Fog City is the one you meant.

What creates a peer
Sharing a channel name and key on the radio, and sharing an area name. Area tags are derived from the name, so two instances that create general independently land in the same conversation — and a typo silently makes a different one.
How they appear
A peer announces itself in a signed NODE record. Your instance learns the ID, the display name and the key from it, without you doing anything. Nothing auto-binds: the display name is a suggestion, and it is yours to accept or ignore.
What does not exist yet
There is no allow list, block list or peer add command. Access control on the mesh is the channel key — anyone with it federates with you. If you need a closed network, run a channel key you have not given away.
What you cannot undo
Nothing on a broadcast medium is unsendable. Taking an area off the mesh stops this node sending its posts; it does not withdraw what peers already hold, because those records are signed and already replicated.
Your identity

Reading your own node ID

It was printed once by meshbbs init and it never changes, because it is BLAKE3(pubkey)[:8] — 64 bits derived from the key in keys/. Two renderings of the same bits: base32 for typing, six words for saying out loud.

Captured from a real runmeshbbs id
$ ./meshbbs id
Node ID
  base32  J9GC-7YKB-JEHCA
  words   mystery-alcohol-write-strong-demand-glad
  short   J9GC7YKB

Display name: fog-city
(self-declared and not authoritative — peers choose their own local alias)

Anyone logged into your board can read it too, without shell access: press N at the main menu. That is the screen to point somebody at when they ask "what's your node ID?"

Their identity

Finding another board's ID

Two ways, and you will usually use both. Once a peer's node record has reached you, its ID is already in peer list — that is the discovery path, and it needs nothing from either sysop. Before that, or to confirm it, ask the operator: the ID is not a secret and the point of a self-certifying identifier is that publishing it is safe.

Captured from a real runmeshbbs peer list
$ ./meshbbs peer list
NODE ID          ALIASES  DISPLAY NAME  SELF
J9GC-7YKB-JEHCA  home     fog-city      yes

Display names are self-declared and not authoritative — always check the ID.

A fresh instance lists only itself, marked SELF. Peers appear as their node records arrive over the mesh — which, on an instance that has just enabled the radio, takes as long as it takes: federation runs on a 15–30 minute batching window, and most scheduled beats are suppressed when they would carry no news.

Naming

Giving a peer a name you will remember

An alias is a local petname, exactly like a Host entry in an SSH config. It is owned by you, resolved locally when a message is composed, and never travels on the wire — so two BBSes may disagree about what pnw means and neither is wrong. That is precisely why no registry needs to exist. 

# either rendering of the ID is accepted
$ ./meshbbs peer alias pnw K7QM-4X2P-B9TFR
$ ./meshbbs peer alias pnw pilot-ranch-obey-vivid-scout-amber

$ ./meshbbs peer resolve pnw       # show both renderings of what a name means
$ ./meshbbs peer list              # every node this instance knows about
$ ./meshbbs peer unalias pnw        # take the name back

Users then address mail as austin@pnw. The alias is resolved to a node ID before anything is sent, and the ID is what goes out.

Trust

Verifying out of band

Address squatting is impossible here, which leaves display-name spoofing as the residual naming attack: nothing stops a node calling itself Fog City. The interface therefore always renders a display name next to its short ID, and never binds a name to an ID on its own — an arriving display name is a suggestion you may accept as an alias with one keystroke.

The check itself is a human one, and it takes ten seconds. Read the six words to the other sysop over voice radio, the phone, or anything that is not the mesh you are about to trust, and have them read theirs back. The ID cannot be spoofed; only your belief about whose it is can be wrong.

Why the words exist at all

Thirteen base32 characters read aloud over a noisy voice channel is a transcription error waiting to happen. Six words are not. The list is the 2048-word BIP-39 English wordlist, vendored and frozen: it is part of the ID's display contract, so reordering it would change how every existing node ID renders. Both forms encode exactly the same 64 bits, and every command accepts either — hyphens or spaces.

Reach

Three ways records travel

Peering is about identity; how the bytes get there is a separate question, and the answer does not have to be the same for every peer.

Meshtastic
The one that makes this project what it is, and the one that costs shared airtime. Attach a radio →
Sneakernet
Carry a file. An exchange is two trips, because a hand-off has no round trip in it: sneakernet export on your board, import on theirs, export --reply-to back, import at home. The reply contains only what you were missing, worked out from the version vectors you sent — no conversation happens, which is what makes it work between boards that have never met. It is also the only way file contents move between boards without IP, since the mesh carries catalogs and never bytes.
Over IP
Mutually-authenticated TLS where each side's certificate is its node key, so the ID is the identity on that link too. The transport is built and tested; there is not yet a configuration surface for pointing an instance at a peer's host, so treat it as present in the code rather than available to a sysop today.
