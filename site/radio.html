Hardware

Attaching a Meshtastic node

A radio is what makes an instance federate. It is not what makes it work — so do this after you have a board running, not before. Six things in order: get a node, find it, configure it, learn what the budget is, measure your mesh, then turn federation on.

Step 1

Which radio, and what firmware

Any Meshtastic node that can be reached over USB serial or over TCP works — meshbbs speaks the standard protobuf stream and does not need custom firmware. Development has been done against Heltec V3 boards on firmware 2.7, and the USB identifier table recognises the chips on the common hardware.

Recognised chips
CP210x (T-Beam, Heltec, RAK), CH9102 (T-Beam, T-Echo), CH340 (Heltec, LilyGO), nRF52840 (RAK4631), Seeed XIAO nRF52840, and ESP32-S3 native USB (Heltec V3, T-Deck). Hardware outside that list is not unsupported — it just will not be identified automatically, and you name its port in the config instead.
Firmware
2.5 or newer. Note one behaviour of 2.5+: unicast is encrypted with the destination's own key, so a direct packet to a peer whose key you have not exchanged is acknowledged by the firmware and never reaches the application. BBS traffic is broadcast on a shared channel, which is why this does not bite in normal operation.
Where it should sit
Somewhere with decent RF, which is rarely the same room as the server. That is the case for the TCP transport: put the radio on a windowsill or in the attic on WiFi, and leave the BBS in the closet.
Flashing it
Nothing meshbbs-specific. Use the official web flasher or the Meshtastic app, get the node talking to the app first, and only then plug it into the BBS. A node that the app cannot see is not a meshbbs problem.
Step 2

Finding your node

Two ways in, and one command that answers both. Serial is the recommended default because nothing can go wrong with it that you cannot see; TCP is better whenever the radio wants to live somewhere the server does not.

Over USB

Plug it in and ask. Detection ranks candidates and explains each guess rather than silently picking one, because most Meshtastic boards use generic USB-UART bridges that anything else might also use.

Captured from a real runmeshbbs mesh ports
$ ./meshbbs mesh ports
/dev/cu.usbserial-0001
    matches a USB serial device name (cu.usbserial*)
Linux
/dev/ttyUSB0 for bridge chips, /dev/ttyACM0 for native USB. Vendor and product IDs are read from sysfs, so the guess here is a real identification. You will need to be in the dialout group — sudo usermod -aG dialout $USER, then log out and back in — or every attempt fails with a permission error.
macOS
/dev/cu.usbserial-*, /dev/cu.usbmodem*, /dev/cu.wchusbserial* or /dev/cu.SLAB_USBtoUART. Use the cu. device and not the tty. one with the same name: the tty. device blocks on open waiting for carrier detect, which looks exactly like a hung program. Reading USB IDs here would need IOKit through cgo, which the project declines, so macOS matches on names — weaker evidence, honestly labelled.
Windows
COM3 and friends, identified by vendor and product ID from the registry. If nothing appears, install the driver for your board's bridge chip (CP210x or CH340) and check Device Manager under Ports (COM & LPT).
Wired to a Pi's UART
Supported, and it will appear in the list — but never ranked above a USB device, because a non-USB serial port is more often a built-in UART or a Bluetooth rfcomm device than a radio.

Over the network

A node on WiFi exposes the same protobuf stream on TCP port 4403. To find its address: in the Meshtastic app, open the node's settings and look under Network, which shows the WiFi status and the address the node was given. Failing that, most nodes answer to meshtastic.local over mDNS, and your router's DHCP lease table always knows. 

# the host may be a name or an address; :4403 is assumed
$ ./meshbbs mesh info --tcp meshtastic.local
$ ./meshbbs mesh info --tcp 192.168.1.42
$ ./meshbbs mesh info --tcp 192.168.1.42:4403

Confirming it, either way

mesh info connects and prints what the node reports about itself. This is the one command to run after every change you make in the app — it is how you find out whether the change took.

$ ./meshbbs mesh info

That is a correctly set up node with one thing still to fix: the metrics update interval is at the firmware default of 30 minutes, which is far too slow for the survey to sample. The next section fixes it.

Step 3

Setting the node up in the Meshtastic app

Five settings, all of them in the official app (Android, iOS, or the web client). meshbbs does not change your radio's configuration — it reads it and works within it — so everything here is done once, in the app, before you enable the mesh.

Region — required

Radio configuration → LoRa → Region. A node with no region set will not transmit at all. US, EU_868, EU_433 and the rest are legal allocations, not preferences: pick the one for where the radio physically is.

Modem preset — leave it at LongFast

Radio configuration → LoRa → Modem preset. Every airtime figure in this project is quoted for LongFast, which carries 233-byte packets in 2.157 seconds. A slower preset buys range and costs you proportionally more of the budget for the same traffic; a faster one does the reverse. Change it only if the whole mesh has.

Hop limit — as low as your topology allows

Radio configuration → LoRa → Hop limit. This is the single most expensive number on the radio: it multiplies what every packet you send costs the whole mesh. The Meshtastic default of 3 is a reasonable starting point and 7 is almost never right. You can also set mesh.hop_limit in meshbbs to override it for BBS traffic only, which is the polite version.

A secondary channel named bbsnet

Radio configuration → Channels → add a channel. Name it bbsnet — matching mesh.channel_name — and give it a key. Every instance that should federate with you needs the same name and the same key; that shared key is what makes you one BBS network rather than several. Share it the way you would any shared secret, not by posting the QR code publicly.

Note that a separate channel is not separate airtime. It keeps BBS traffic logically apart so that non-BBS nodes ignore it, but every channel on the frequency shares the same seconds. Only the governor makes you a good neighbour.

Telemetry every 60 seconds

Module configuration → Telemetry → Device metrics update interval → 60. The node reports channel utilisation in its device metrics, and that is the measurement the survey reads. A stock node updates every 30 minutes, which is far too slow to sample — you would get a handful of readings across a two-hour run. Set this before surveying; you can put it back afterwards.

If you want the radio on WiFi

Radio configuration → Network — enable WiFi, give it your SSID and password, and save. The node reboots and joins; its address then shows on the same screen. That is the address you pass as mesh.tcp_host. Serial and WiFi are not exclusive, so it is fine to configure over USB and then run over TCP.

Check your work

Run meshbbs mesh info again. Region, preset, hop limit, the bbsnet channel and the telemetry interval are all in that output, and if one of them did not save you will see it there rather than discovering it during a two-hour survey.

Step 4

The words this project uses

meshbbs talks about airtime in terms that are specific to it. Here they are once, with the answer to "so what should I set it to?" attached — because for most of them the answer is "nothing, leave it".

Airtime
seconds on the channel
How long a transmission occupies the frequency. One full 233-byte packet on LongFast is 2.157 seconds. Radio is a shared medium: while you are transmitting, nobody else on that frequency can. Airtime, not bandwidth, is the scarce thing here.
R, the flood multiplier
default 4 — measure it
Meshtastic uses managed flooding: every node that hears a broadcast rebroadcasts it. So one transmission of yours costs the channel roughly R times what it costs you. R is a property of your mesh's RF topology seen from your position — it cannot be derived, simulated or guessed well, and 4 is a placeholder. Every airtime figure scales linearly with it. Measure it rather than tuning it.
Hop limit
set it low
How many times a packet may be relayed onward. It is a direct multiplier on reach and on cost. Raising it is the fastest way to make your instance expensive for everybody else.
The ceiling
5% — leave it
mesh.airtime_ceiling_pct is the share of the channel that the whole BBS network should occupy — not your share. It is deliberately small: a BBS is a guest on a mesh built for other things. The code clamps it at 15 whatever you write.
The budget
derived, not set
Your instance's allowance: the ceiling divided by expected_instance_count, then adjusted for R. You never set this. It is computed, and meshbbs serve prints it at startup in packets and posts per day, because a percentage is not a thing anybody can reason about.
The governor
always on
The component that spends the budget: it batches, prioritises, defers and refuses. It is why an instance cannot flood the mesh even if its sysop has misconfigured everything else, and it is not switchable.
Quiet hours
optional
Local-time windows in which this node transmits nothing at all, e.g. 22:00-06:00. Windows may wrap midnight. Worth setting if your radio shares a neighbourhood with people who notice.
bbsnet
the channel
The secondary Meshtastic channel that carries BBS traffic, named by mesh.channel_name. Same name and key on every instance in your network.
Step 4, continued

What the budget actually buys

Share a 5% ceiling across fifty instances and each one gets about 21 seconds of transmit time a day. Ten full packets. That is the number every other decision in the design answers to, and it is worth internalising before you federate anything.

Three consequences worth knowing up front. Posts are batched over a 15–30 minute window rather than sent as they are written, so federation is not chat. File contents never cross the mesh at any size — only catalogs replicate, and bytes move over IP or on a memory stick. And a busy area can exhaust a day's allowance, which is what meshbbs area share exists to bound.

Step 5

Measuring R on your mesh

mesh survey needs only the radio — no database, no SSH server, no config beyond the device connection. It listens with the radio silent to establish a baseline, transmits a small paced load at each hop limit, and attributes the rise in channel utilisation to rebroadcasts of its own packets.

It prints the plan and refuses to start until you have read it. This command transmits. It is polite about it — it will not start on a busy channel, aborts if the channel gets busier, and defaults to about 1% duty — but it does put packets on a shared band for as long as you tell it to.

Captured from a real runmeshbbs mesh survey
$ ./meshbbs mesh survey
Survey plan
  radio          LONG_FAST (SF11, BW250kHz, CR4/5)
  baseline       30m0s, silent — twice, before and after
  load           30m0s at each of hop [1 3 5]
  total time     2h30m0s
  transmits      about 27 packets of 200 bytes
  our airtime    about 52s (before rebroadcasts)

Error: not transmitting: re-run with --yes once the plan above looks right

$ ./meshbbs mesh survey --yes --out fog-city-survey.txt
Before you start
Set the telemetry interval to 60s (step 3), pick a couple of hours when the mesh is quiet, and leave the radio where it will actually live — R is measured from a position, and moving the antenna afterwards invalidates it.
Shorter runs
--baseline 10m --load 10m --hops 3 gives a rough number in about 40 minutes. The defaults are long because the measurement is a difference between two noisy quantities, and confidence comes from samples.
Reading the result
The report ends with "what this means for your instance": R at the best hop limit, and what that buys in seconds, full packets and short posts per day. It also reports ambient drift between the opening and closing baselines — if the mesh got busier while you were transmitting, your R is overstated and the report says so.
If it fails to measure
"No usable R was measured" means the load never rose above the channel's own noise. That is an honest answer rather than an error: re-run when the mesh is quieter, or with a longer load phase. A quiet mesh with no neighbours has no rebroadcasts to measure — R really is near 1 there.
Then what
Put the number in mesh.flood_multiplier. The report is plain text on purpose: sysops send them to each other, and the project aggregates them into a distribution that eventually replaces the guessed default for everyone.
Step 6

Turning federation on

Two lines of config and a restart. The mesh comes up before the SSH server accepts anyone, so a misconfigured radio, an absent channel or a ham-mode violation stops startup instead of leaving an instance that looks healthy and silently federates nothing.

The minimumconfig.toml
[mesh]
enabled          = true
serial_device    = "/dev/ttyUSB0"   # or leave empty to auto-detect
hop_limit        = 3
flood_multiplier = 5.2               # whatever the survey measured

Restart, and the startup banner grows three lines: the transport and channel, the radio's own hardware, preset and hop limit, and the derived airtime budget in human terms. Then federate an area — meshbbs area federate general — and grant somebody post_federated. Neither happens by itself.

Licensed operators, read this first

If your node reports a licensed operator (Meshtastic's ham mode), meshbbs blocks encrypted traffic rather than let you stumble into an FCC Part 97 violation: Part 97 prohibits messages encoded to obscure their meaning, and a channel PSK is exactly that. The override exists — mesh.ham_mode_override = "i_accept_part97_responsibility" — and the licence at risk is yours.

What is not restricted matters more: signatures authenticate without obscuring anything, so a ham-mode instance federates forums, node records and succession normally. It gives up private mail over the mesh, and nothing else.
