Operations

When it doesn't work

Most failures here are loud on purpose: an instance that refuses to start beats one that starts wrong. The exceptions — the ones that fail silently — are on this page too, and they are the ones worth reading before you need them.

Startup

It refuses to start

Run meshbbs config check first, every time. It exits non-zero with a precise message, and it is the same validation serve runs — so if check is happy, the config is not your problem.

Unknown key
A typo is fatal by design. airtime_ceiling_percent is not airtime_ceiling_pct, and silently ignoring the difference is how a mesh gets flooded. Check spelling against the reference.
Key permissions
The keys directory must be 0700 and the keys inside it 0600. A restore from an archive that did not preserve modes is the usual cause: chmod 700 keys && chmod 600 keys/*.
web.enabled without an origin
Deliberate. The origin has no default because a wrong one fails every sign-in with no useful error, so it is caught here instead.
Ham-mode conflict
The radio reports a licensed operator and the configuration would encrypt traffic. Either turn off ham mode on the radio, or accept the override — and its consequences — explicitly.
Address already in use
Another instance is running, or something else holds the port. Port 2222 is the default precisely so that this is rare; port 22 also needs root or CAP_NET_BIND_SERVICE.
"dev commands refuse to run"
Working as intended: node.environment is production. The meshbbs dev subcommands only run against an instance marked development, which is a datadir you are willing to lose.
The mesh stops startup
Also intended. The radio link comes up before SSH accepts anyone, so a missing channel or an unreachable node fails loudly rather than leaving an instance that looks healthy and federates nothing.
Hardware

The radio isn't found, or stops answering

Start with meshbbs mesh ports and meshbbs mesh info. Between them they distinguish "no device", "wrong device", "no permission" and "device is there but the firmware is unhappy", which are four quite different problems.

Nothing listed
On Linux and Windows, detection reads USB vendor and product IDs, so an empty list usually means the OS has not enumerated the device — try another cable, and on Windows install the CP210x or CH340 driver. On macOS detection matches device names, so an unusual adapter can be missed even when it works: name the port directly with mesh.serial_device.
Permission denied (Linux)
You are not in the dialout group. sudo usermod -aG dialout $USER, then log out and back in — the new group does not apply to an existing session.
It hangs on open (macOS)
You are on the /dev/tty.* device, which blocks waiting for carrier detect. Use the /dev/cu.* device with the same name.
Wrong port picked
Detection ranks candidates and explains each guess; it never claims certainty, because most Meshtastic boards use generic USB-UART bridges that anything might use. Set mesh.serial_device and the guessing stops.
It worked, then went quiet
A USB serial handle can go one-way: writes keep succeeding and transmissions go out while nothing is ever received, and only silence reveals it. mesh.rx_timeout_secs (default 300) reconnects when the radio has sent nothing for that long. Do not set it below about 60 — a busy-but-quiet radio gets reconnected needlessly, and each reconnect re-announces.
TCP node unreachable
Confirm the address on the node's Network screen in the Meshtastic app, then meshbbs mesh info --tcp <host>. Port 4403 is assumed if you do not give one. A node that dropped off WiFi usually took a new DHCP lease.
Federation

The radio is up but nothing federates

Federation has more off-switches than anything else in the system, all of them deliberate. Work down this list in order — it is roughly the order of how often each one is the answer.

Is the area federated?
Areas are local-only when created. meshbbs area list shows the scope of each; meshbbs area federate general changes it.
Does the poster have the capability?
New accounts never get post_federated, whatever the registration mode. meshbbs user show bob shows what they have.
Same channel, same key?
Both sides need a secondary channel with matching name and key. meshbbs mesh info lists the channels the radio actually has, which is the only opinion that counts.
Same area name, exactly?
Area tags are derived from names, so general and General are different conversations and nothing warns you. meshbbs area list prints the derived tag — compare it with your peer's.
Have you waited long enough?
Records are batched over a 15–30 minute window and most scheduled beats are suppressed when they carry no news. Federation is not chat, and an hour of quiet after the first post is normal.
Is the budget exhausted?
The governor defers rather than drops. If an area is monopolising the allowance, meshbbs area share caps it as a fraction of the whole budget.
Quiet hours?
A node in a mesh.quiet_hours window transmits nothing at all. That is the setting doing its job.
A development instance that restarted
Packet IDs are part of the wire contract, so a deterministically seeded node re-uses IDs the mesh has already seen after a restart and its packets are dropped as duplicates — it looks like a node that has gone mute. Real hardware taught this one, and it only affects seeded development instances.
Browser front end

Passkeys fail, and say nothing useful

Almost always web.origin. Passkeys are bound to an origin, and a mismatch does not degrade gracefully — the browser refuses with an error that says nothing about the cause. Scheme, host and port must match exactly what the browser sends.

Sign-in always fails
Compare web.origin with the address bar, character for character. https://bbs.example.com and https://bbs.example.com:8443 are different origins.
Enrolment code rejected
Codes expire in ten minutes and enrolment is rate-limited to ten attempts an hour per client. Press P in the SSH session again for a fresh one.
Everyone rate-limited at once
You are behind a reverse proxy and web.trusted_proxies is empty, so every request is attributed to the proxy's address and all clients share one allowance. List the proxy — and only proxies you run, because any address listed can claim to be any client.
No certificate yet
Bind to loopback. Browsers treat http://localhost as a secure context, so the web UI works there with no certificate at all — which is the sane way to try it before you own a domain.
Before you need it

What to back up, and how

Two things, with completely different risk profiles. keys/ is irreplaceable and should be backed up immediately, everywhere, forever. bbs.db is replaceable in the sense that a restore is possible — and dangerous in a way that is worth understanding before you are in a hurry.

keys/
Back it up now. Copy it off the machine. Preserve permissions — 0700 on the directory, 0600 on the keys. There is no downside and no risk: restoring a key changes nothing about your position in the network, because the key is your position in the network.
bbs.db
Stop the server, copy the file, start it again. That is the safe procedure. A copy taken while the server is running may be mid-transaction; if you must, use sqlite3 bbs.db ".backup snapshot.db", which is transaction-aware.
config.toml
Worth keeping, trivially reconstructable. It is a dozen lines of settings you chose, not state.
files/
Your file areas. Ordinary data — back it up like any other directory. The catalog lives in the database, the bytes live here.
The dangerous one

Restoring the database is not a routine operation

Every record this instance publishes carries a sequence number, and peers remember which ones they have seen. Restore a week-old database and the instance starts reissuing sequence numbers that peers already hold — with different content behind them.

The consequence is worth stating plainly: the divergence is permanent and completely silent. No error, no conflict, no repair. Peers simply hold different records under identical coordinates, forever, and every future comparison between those logs is meaningless.

What the software can and cannot catch

At startup, meshbbs compares the durable high-water mark against the highest sequence number actually in its own log. If the mark is behind — a restore that rolled back the counter but not the records, or vice versa — it repairs the mark and bumps an incarnation counter, which is the signal peers use to re-verify this origin's log rather than assume continuity. Every area is checked, and one regression anywhere bumps the incarnation once for all of them.

What it cannot catch is a consistent rollback: a whole database restored to an older state, records and counter together, looks exactly like a node that has simply published less. Nothing local can tell the difference. That case is on you.

Prefer this instead
If the instance is broken but the key survives, consider starting from an empty database rather than an old one. You lose local history; you do not corrupt the network's view of you. Peers will re-send what they hold.
If you must restore
Restore, then start the server and read the log. A warning about a repaired high-water mark and an incremented incarnation counter is the expected outcome and means the safety net caught it. No warning after a restore of an older database is the case to worry about.
Tell your peers
This is a social protocol as much as a technical one. If you have restored a backup, say so on whatever channel your network uses. Sysops who know can compare.
The unrecoverable one

A lost node key

Cannot be recovered. Not by us, not by your peers, not by anyone — the ID is derived from the key, so with no key there is nothing to sign with and nothing that proves the new instance is a continuation of the old one.

The protocol has a record type for exactly this — a signed succession record, by which a node hands its identity to a new key — but signing one requires the old key, so it is a planned handover and not a recovery path. There is no sysop command for it yet.

In practice: a lost key means re-initialising. The instance rejoins under a new ID, its history is not attributable to it, and every peer that had named it needs to re-alias. This is the whole reason step three of the quick start is "back up keys/" and not something more interesting.
