04 Run a node

One binary, no runtime

Pure Go with CGO_ENABLED=0 on every target — no build tags, no cgo variants, no split release artifacts. Building needs nothing but a Go toolchain, and running needs nothing at all: no database server, no Node, no C libraries. The browser front end is embedded in the binary too, so there's no CDN and no asset build in the release path.

First run

Four commands to a working BBS

Federation is off until you turn it on, so this gets you a complete single-node board with forums, private mail, file areas and node chat — no radio required.

Build

Linux, macOS and Windows, on amd64 and arm64.

$ go build -o meshbbs ./cmd/meshbbs

Initialise

This generates your node key. There is no address to choose, request or register — the node ID is derived from the key itself.

$ ./meshbbs init --display-name fog-city \
      --sysop-nick austin --sysop-password-stdin

  ✓ node key generated  keys/node.ed25519
  ✓ node id  K7QM-4X2P-B9TFR
           pilot ranch obey vivid scout amber
  ✓ database  bbs.db
  ✓ sysop account  austin

Back up keys/

Before anything else. A lost node key cannot be recovered — with no key there is nothing to sign a succession record with, and the instance would have to re-establish with its peers as an entirely new node. The first-run wizard says so and offers to print the key as a recovery phrase.

Serve

Port 2222 by default, which avoids needing root. Use 22 on a dedicated host.

$ ./meshbbs serve
  ssh listening on :2222 · 4 areas · 0 peers

$ ssh austin@localhost -p 2222

Optionally, open the second door

The browser front end is off until you give it an origin and a certificate. Then get your first passkey across by pressing P in an SSH session and typing the code it shows into the sign-in page.

# in your config file
[web]
enabled  = true
origin   = "https://bbs.example.com"   # required — passkeys bind to it
tls_cert = "/etc/meshbbs/fullchain.pem"
tls_key  = "/etc/meshbbs/privkey.pem"

$ ./meshbbs config check   # catches a missing origin before restart
$ ./meshbbs serve
  ssh listening on :2222 · web listening on :8443
Don't restore bbs.db from a backup casually

Restoring a week-old database reissues sequence numbers that peers have already seen, with different content behind them. The divergence is permanent and completely silent — no error, no conflict, peers just hold different records under identical coordinates forever. meshbbs detects the regression at startup and flags it to peers via an incarnation counter, but restoring the database is not a routine operation.

Administration

Accounts, capabilities and areas

Everything the sysop terminal does is also a subcommand, so it's all scriptable. Cobra generates the help and shell completions. 

# accounts
$ ./meshbbs user add bob
  New accounts cannot post to federated areas by default —
  the door is open, the shared airtime is gated.

$ ./meshbbs user grant bob post_federated
$ ./meshbbs user list
$ ./meshbbs user show bob
$ ./meshbbs user passwd bob
$ ./meshbbs user revoke bob post_federated

# message areas — new areas are local-only until you say otherwise
$ ./meshbbs area create general
$ ./meshbbs area federate general
$ ./meshbbs area list

# your own identity, in both renderings
$ ./meshbbs id
  K7QM-4X2P-B9TFR
  pilot ranch obey vivid scout amber
Hardware

Attaching a Meshtastic node

Over USB serial or over TCP to a node on WiFi — both speak the same protobuf stream. Serial is the recommended default; TCP is better when the radio is mounted somewhere with decent RF rather than in the server closet. 

$ ./meshbbs mesh ports
  Ranked candidates, with the reasoning for each:
  1. /dev/cu.usbmodem14201  name matches a known USB-UART pattern
  2. /dev/cu.usbserial-0001  generic bridge, weaker evidence

$ ./meshbbs mesh info
$ ./meshbbs mesh info --tcp mesh.local

# measure YOUR mesh before trusting the default budget
$ ./meshbbs mesh survey
Why ports are ranked
Reading USB vendor and product IDs is pure Go on Linux and Windows, but on macOS it needs IOKit through cgo — which is non-negotiable to avoid. So macOS matches device names instead, which is weaker evidence, and detection explains each guess rather than silently picking one. Most Meshtastic boards use generic USB-UART bridges anyway, so even a vendor-ID match identifies a chip, not a radio.
Run the survey first
It needs only the radio — no database, no SSH server, no config beyond the device connection. It measures the flood multiplier on your mesh, sweeps the hop limit to show what each hop costs the commons, and reports your derived budget in real terms: "at R = 5.2, your instance can originate about 8 full packets a day, roughly 20 short posts."
Set the hop limit low
Hop limit is a direct multiplier on what everything you send costs the mesh. Set it explicitly, as low as your topology allows. The survey tells you what "as low as" means for your deployment.
Channel setup
Create a secondary channel — bbsnet by default — with the same name and key on every instance, using the Meshtastic app. Note that a separate channel is not separate airtime; it keeps BBS traffic logically apart so non-BBS nodes can ignore it, but only the governor makes you a good neighbour.
Federation

Peering is an ID exchange

There's no registration and no pairing ceremony. You add a peer's node ID to your allow list — and because the ID is the key, allowlisting an ID is allowlisting a key. There is nothing to get wrong and no way for a different key to answer to that ID.

Then you give it a local name, the way you'd name a host in an SSH config. That name is yours alone and never travels on the wire. 

$ ./meshbbs peer alias pnw K7QM4X2PB9TFR
  Local petname only. Never goes on the wire — two BBSes
  may disagree about what 'pnw' means and neither is wrong.

$ ./meshbbs peer list
$ ./meshbbs peer resolve pnw
$ ./meshbbs peer unalias pnw
Verify out of band

When a peer's node record arrives, its display name is a suggestion you may accept as an alias with one keystroke — nothing ever auto-binds. Display-name spoofing is the residual naming attack now that address squatting is impossible: nothing stops a node calling itself Fog City, so the interface always renders a display name next to its short ID. The ID itself cannot be spoofed. The six-word rendering exists for confirming a fingerprint over voice radio or the phone.

Configuration

One TOML file, strictly validated

An unknown key is a startup error, not a silently ignored line. Config is hot-reloadable, so a sysop can iterate on a theme without dropping sessions, and every setting has an environment-variable equivalent. 

$ ./meshbbs config check       # validate before restarting
$ ./meshbbs config show        # effective values, after precedence
$ ./meshbbs config reference   # every setting, generated from source

The settings that matter most

A selection. meshbbs config reference generates the complete list from the source, so it can't drift.

mesh.enabled
false
Federate over a radio. Off by default, because enabling it transmits on a shared band.
mesh.airtime_ceiling_pct
5
The share of the channel the whole BBS network should use, divided by the expected instance count to get this node's allowance. Clamped to 15 in code.
mesh.flood_multiplier
4
R — how many times the mesh rebroadcasts each packet. Every airtime figure scales linearly with it, and 4 is a guess. Run the survey to measure yours.
mesh.hop_limit
0 — use the radio's own
Multiplies what every packet costs the mesh, so set it as low as your topology allows.
mesh.quiet_hours
Local-time windows of zero transmission, e.g. 22:00-06:00. Windows may wrap midnight.
users.registration_mode
open
Open, approval, invite or closed. Open with federated posting withheld is the default.
web.enabled
false
Serve the browser front end. Off by default, because it needs a public origin and a TLS certificate and neither has a sensible default.
web.origin
required when enabled
The public origin browsers reach you at, e.g. https://bbs.example.com. Get this wrong and it does not degrade — passkeys are bound to it, so every sign-in fails with a browser error that says nothing about the cause. Which is why it has no default and is validated at startup.
web.unlocked_idle_timeout_mins
10 — vs 30 idle
Shorter on purpose. A session with mail unlocked holds the passphrase in memory, and a closing browser tab is a far less reliable goodbye than an SSH disconnect.
web.enrol_attempts_per_hour
10
Passkey-enrolment code attempts per client. Someone typing a code off their own terminal needs two or three; a script guessing needs far more. Note that X-Forwarded-For is not trusted, so behind a reverse proxy this becomes one shared allowance.
telnet.enabled
false
Off by default: telnet is plaintext, so anything typed can be read by anyone on the network path. telnet.guest_only defaults to true and is the recommended middle setting.
mesh.ham_mode_override
Set to i_accept_part97_responsibility to transmit encrypted traffic while the radio reports a licensed operator. Part 97 prohibits obscuring the meaning of amateur transmissions; the licence at risk is yours.

Where the project is

Status and roadmap

Phase 2 is complete: a usable single-node BBS, the sync protocol and its simulator, and instances able to federate over IP. Phase 3 is in progress — the Meshtastic link itself, so federation over the mesh does not work yet.

The first two-radio bring-up has run: two Heltec V3s on a bbsnet channel, with discovery, broadcast in both directions and attribution all working. Two things hardware taught that no amount of simulation would — packet IDs are part of the wire contract, so a deterministically seeded node goes silent after a restart; and firmware 2.5+ encrypts unicast with the destination's own key, so a direct packet to a peer whose key you haven't exchanged is acknowledged by the firmware and never seen by the application.

0 — Skeleton ✓
Config loader, SQLite schema, node key and ID, alias table, command tree, account CLI, injected clock and seeded RNG, CI cross-compiling all five targets cgo-free.
1 — Single-node BBS ✓
SSH server, signup, capability grants, the terminal interface, themes, local forums and mail with passphrase-wrapped keys, file areas over SFTP, node chat, the sysop panel.
2 — Federation over IP ✓
Record log, version vectors, anti-entropy, bundle format, zstd dictionary, the fountain codec, succession records, the deterministic simulator and its property, invariant and fuzz suites.
3 — Meshtastic link →
In progress. Serial and TCP transports, protobuf framing, the airtime governor with flood-multiplier accounting, ham-mode safety checks, file catalog replication, the mesh survey and live R estimation.
4 — Doors
The modern door API and its capability model, PTY and ConPTY bridging, sandboxing, reference doors. Independent of federation.
Web front end ✓
Shipped out of order, ahead of the phase it was scheduled in. The screen model was split from its rendering, then a browser renderer, passkey auth and a session bridge were built on top. It arrived as a semantic terminal rather than the xterm.js stopgap originally planned — see using it.
5 — Reach
What's left of it: inter-BBS door events, sneakernet bundles, and the client-held key helper.
6 — Interop
Freeze the wire format, publish a spec and conformance vectors, request a registered Meshtastic port number, ship the FidoNet gateway. The first point at which the project makes promises to strangers, and not to be rushed toward.
7 — Legacy DOS doors
A DOSBox-X bridge. Nice-to-have; may never ship, and nothing depends on it.

How it gets tested

Deterministic simulation is the centrepiece, because it's how the federation protocol gets tested at all. That depends on domain code never calling time.Now() or package-level rand, and never letting map iteration order reach output bytes — the last of which would silently corrupt record signatures. A checker enforces it: 

$ go test ./...
$ go run ./tools/checkdeterminism ./...
$ go test ./internal/tui/ -update   # regenerate golden screens

Nearly every measured number on this site — convergence times, channel utilisation, the coding overhead constants, the publish ceiling — came out of that simulator rather than a whiteboard. Several of them contradicted what an earlier draft of the design assumed, which is the whole reason it exists.
